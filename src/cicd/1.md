**Typical flow for a Spring Boot microservice on EC2 with Bitbucket Pipelines / GitHub Actions**

**1. Trigger**
Pipeline kicks off on a push/merge to a specific branch — usually `develop`/`main` for auto-deploy to lower environments, and a tag or manual approval gate for production.

**2. Build stage**
- Checkout code.
- Run `mvn clean package` (or `./gradlew build`) — compiles, runs unit tests, and produces the JAR/WAR artifact.
- Fail fast here if tests fail — nothing downstream should run on broken code.

**3. Static analysis / quality gates (if configured)**
- SonarQube scan, checkstyle, or similar for code quality.
- Dependency vulnerability scan (e.g., OWASP dependency-check, Snyk) — increasingly common in fintech pipelines given compliance requirements.

**4. Package/containerize**
- If using Docker: build image, tag with commit SHA or version, push to a registry (ECR most likely on AWS).
- If deploying JAR directly to EC2 (no containers): package artifact and prepare for transfer instead.

**5. Deploy to EC2**
Common approaches here, worth stating clearly which one your project uses:
- **SSH-based deploy**: pipeline SSHs into the EC2 instance (or uses AWS Systems Manager `Send-Command`), pulls the new artifact/image, restarts the service (`systemctl restart <service>` or a Docker container recreate).
- **CodeDeploy**: pipeline uploads the artifact to S3, triggers AWS CodeDeploy, which handles the actual rollout to EC2 instances (supports in-place or blue-green deployment).
- **Blue-green / rolling via load balancer**: new instances (or a new target group) are brought up behind the ALB, health-checked, then traffic is shifted — old instances drained and terminated. Reduces downtime vs a straight restart.

**6. Environment-specific configuration**
- Secrets/config pulled from AWS Secrets Manager or Parameter Store at deploy/runtime — not baked into the artifact or repo.
- Environment variables or Spring profiles (`application-prod.yml` vs `application-dev.yml`) select the right config per environment.

**7. Post-deploy verification**
- Health check endpoint (Spring Boot Actuator `/actuator/health`) polled before marking deploy successful.
- Smoke tests or a basic integration test suite run against the newly deployed environment.

**8. Rollback strategy**
- Keep the previous artifact/AMI/image tagged and ready — rollback is redeploying the last known-good version if health checks fail post-deploy.
