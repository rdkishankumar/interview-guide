# 16. Advanced Internal Questions
 * `1. Explain HashMap internals in Java 8 step by step.`
    In Java 8, `HashMap` is implemented using an **array of buckets**, where each bucket holds either a **singly linked list** or a self-balancing **Red-Black Tree** to store key-value pairs (`Node<K,V>` or `TreeNode<K,V>`).

---

### 1. Core Data Structures & Constants

* **Bucket Array (`Node<K,V>[] table`):** The primary backing array.
* **`DEFAULT_INITIAL_CAPACITY`:** `16` ($2^4$). Always a power of 2.
* **`DEFAULT_LOAD_FACTOR`:** `0.75`. Controls when the table resizes.
* **`TREEIFY_THRESHOLD`:** `8`. When collisions in a single bucket reach 8 nodes, it converts to a Red-Black Tree.
* **`UNTREEIFY_THRESHOLD`:** `6`. When a tree bucket shrinks to 6 nodes during resize/removal, it reverts to a linked list.
* **`MIN_TREEIFY_CAPACITY`:** `64`. A bucket will treeify only if the total array capacity is at least 64; otherwise, it resizes the array instead.

---

### 2. Step 1: Calculating the Hash (Perturbation Function)

When you pass a key, Java first calls `key.hashCode()` and applies a bitwise shift/XOR operation:

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

```

* **Why the XOR and shift?** It mixes the high 16 bits into the low 16 bits. Since table sizes are small powers of 2 (e.g., 16), only the lower bits determine the index. This mixing drastically reduces collisions from poor `hashCode()` implementations.

---

### 3. Step 2: Finding the Bucket Index

The bucket index is calculated using a bitwise AND instead of modulo:

$$\text{index} = (n - 1) \ \& \ \text{hash}$$

*(Where $n$ is the current table length, which is always a power of 2).*

* Because $n$ is a power of 2, $(n - 1) \ \& \ \text{hash}$ is mathematically equivalent to $\text{hash} \pmod n$, but runs in a single CPU cycle.

---

### 4. Step 3: Inserting Data (`put(K, V)`)

```text
put(key, value)
  │
  ├── 1. Array empty/null? ──► Initialize array (resize to capacity 16).
  │
  ├── 2. Bucket empty? ──► Create new Node<K,V> at table[index].
  │
  └── 3. Collision occurs (table[index] not empty):
        │
        ├── Key matches first node (same hash && (k == key || key.equals(k)))?
        │     └── Overwrite existing value.
        │
        ├── Is bucket a TreeNode?
        │     └── Insert into Red-Black Tree (O(log n)).
        │
        └── Is bucket a standard LinkedList?
              ├── Traverse to tail (append node at the end - tail insertion).
              ├── If matching key found during traversal, overwrite value.
              └── If node count reaches 8:
                    ├── If table.length < 64 ──► Resize array instead.
                    └── If table.length >= 64 ──► Convert bucket to Red-Black Tree.

```

---

### 5. Step 4: Retrieving Data (`get(K)`)

1. Compute `hash = hash(key)` and locate `table[(n - 1) & hash]`.
2. Check the first node in the bucket:
* If `first.hash == hash` and `(first.key == key || key.equals(first.key))`, return `first.value`.


3. If not matched:
* If it's a `TreeNode`, search the Red-Black Tree in **$O(\log n)$** time.
* If it's a `Node`, traverse the linked list in **$O(n)$** time.


4. If no match is found after traversing, return `null`.

---

### 6. Step 5: Resizing & Rehashing (`resize()`)

When `size > threshold` ($\text{capacity} \times \text{load\_factor}$, e.g., $16 \times 0.75 = 12$), the array doubles in capacity ($16 \rightarrow 32$).

**Java 8 Optimization (No full re-indexing):**

* Because capacity doubles ($2^x$), a node's new index in the doubled table is either:
* Its **same old index** (`oldIndex`)
* **Old index + old capacity** (`oldIndex + oldCap`)


* Java 8 checks the new bit using `(e.hash & oldCap) == 0`:
* If `0` $\rightarrow$ stays at `oldIndex`.
* If `!= 0` $\rightarrow$ moves to `oldIndex + oldCap`.


* It preserves the original relative order (no reverse-order insertion), which eliminates the infamous Java 7 **infinite loop / cyclic dependency** bug during concurrent resizes.

# 2. Explain ArrayList internals in Java 8.

`ArrayList` in Java is a resizable, index-based list backed by a standard **Object array (`transient Object[] elementData`)**.

It provides fast random access by index and dynamically grows its underlying array when capacity runs out.

---

### 1. Key Fields & Constants in Java 8

* `transient Object[] elementData`: The internal buffer array where elements are stored.
* `private int size`: The number of elements currently stored in the list.
* `DEFAULT_CAPACITY = 10`: The initial capacity assigned when elements are first added to an empty list.
* `DEFAULTCAPACITY_EMPTY_ELEMENTDATA = {}`: A shared empty array used when `new ArrayList<>()` is instantiated without parameters.
* `EMPTY_ELEMENTDATA = {}`: A shared empty array used when `new ArrayList<>(0)` is explicitly initialized with a capacity of 0.

---

### 2. Initialization & Lazy Allocation

In Java 8, instantiating `new ArrayList<>()` uses **lazy allocation** to save heap memory:

```java
public ArrayList() {
    this.elementData = DEFAULTCAPACITY_EMPTY_ELEMENTDATA;
}

```

* Creating an `ArrayList` allocates **no heap memory** for the internal array initially.
* Memory allocation for the default capacity of **10** is deferred until the very first call to `.add()`.

---

### 3. Adding Elements & Growth Formula (`grow()`)

When you call `list.add(element)`:

1. It verifies whether `size + 1` exceeds `elementData.length`.
2. If full, it calls `grow(minCapacity)`.

```java
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    // New capacity = oldCapacity + (oldCapacity >> 1)  --> 1.5x (50% growth)
    int newCapacity = oldCapacity + (oldCapacity >> 1);
    
    if (newCapacity - minCapacity < 0)
        newCapacity = minCapacity;
    if (newCapacity - MAX_ARRAY_SIZE > 0)
        newCapacity = hugeCapacity(minCapacity);
        
    // Native array copy to the new larger array
    elementData = Arrays.copyOf(elementData, newCapacity);
}

```

* **Growth Factor:** The array expands by **50% ($1.5\times$)** of its current capacity using bitwise right-shift (`oldCapacity + (oldCapacity >> 1)`).
* **Array Copying:** Memory reallocation uses `System.arraycopy()` via `Arrays.copyOf()`, which copies elements directly at the native OS memory level.

---

### 4. Insertions, Deletions, and Shifting

* **Positional Add (`add(index, element)`):**
* Checks bounds (`index >= 0 && index <= size`).
* Shifts elements starting at `index` one position to the right via `System.arraycopy()`.
* Inserts the new element at `index` and increments `size`.
* Time Complexity: **$O(n)$** due to shifting.


* **Removal (`remove(index)`):**
* Calculates `numMoved = size - index - 1`.
* Shifts elements to the left by one position.
* Sets the last slot `elementData[--size] = null` so the **Garbage Collector** can reclaim the dereferenced object.
* Time Complexity: **$O(n)$**.



---

### 5. Fail-Fast Iterators (`modCount`)

`ArrayList` tracks structural modifications (adding, removing, resizing) using an inherited counter named `modCount`.

* Every time an iterator is created, it takes a snapshot: `expectedModCount = modCount`.
* During iteration (`next()`, `remove()`), it checks `if (modCount != expectedModCount)`.
* If another thread or code modifies the list structurally outside the iterator, it immediately throws `ConcurrentModificationException`.

---

### Performance Summary

| Operation | Time Complexity | Notes |
| --- | --- | --- |
| **`get(index)` / `set(index, val)**` | **$O(1)$** | Direct memory offset lookup |
| **`add(element)` (Append)** | **Amortized $O(1)$** | $O(n)$ only when array needs resizing |
| **`add(index, element)`** | **$O(n)$** | Requires right-shifting elements |
| **`remove(index)`** | **$O(n)$** | Requires left-shifting elements |
| **`contains(element)` / `indexOf**` | **$O(n)$** | Linear scan across array |

# 3. Internal working of CopyOnArrayList
# CopyOnWriteArrayList

## Overview

* ArrayList and LinkedList are not thread safe and concurrent modifications by multiple threads can lead to unexpected behavior.
* ConcurrentModificationException mainly happens when:

    * One thread is trying to traverse or iterate over your collection.
    * Meanwhile another thread comes in and tries to modify.
    * Modify means:

        * Add an element
        * Remove an element
        * Update an element
* One thread is not modifying, it is just reading.
* Another thread is trying to modify.
* That is a clash and a conflict because it is manipulating the same collection.
* That leads to ConcurrentModificationException.
* ConcurrentModificationException is very prevalent when there are multiple threads at play and unexpected behavior happens in case of ArrayList and LinkedList.
* It doesn't mean that ConcurrentModificationException only happens with ArrayList and LinkedList. It also happens with HashMap, but for now the discussion is around ArrayList and LinkedList because it is the List kind of thing that we are talking about.

## Thread-Safe Options Before CopyOnWriteArrayList

To get over ConcurrentModificationException, CopyOnWriteArrayList has come in.

Whenever there are multiple threads coming into play, ConcurrentModificationException is bound to happen if it is unsynchronized, like you do not have any external synchronization mechanism for ArrayList and LinkedList. Hence they're not thread safe.

There have been more thread safe options before also:

### Vector

* Vector class is a legacy class.
* It was thread safe.
* It locks the entire list.
* If you have the list, the entire list will be locked for each and every operation.
* Whether it is a read operation or it is a write operation, your entire list is going to be locked.
* This is why the performance is taking a hit.
* It is slow.
* It is a legacy class.
* Vector is not going to suit our use cases in modern applications.

### Collections.synchronizedList

In the Collections utility, in the Collections class, there are a couple of utility methods:

* `Collections.synchronizedList`
* `Collections.synchronizedSet`

If you use this, this is also providing a synchronization mechanism through which ConcurrentModificationException can be avoided.

This means I basically want to have thread safe code and these are the measures which I can take:

* I can use a Vector class.
* I can use Collections class `synchronizedList`.

`SynchronizedList` is a static method.

Collections.synchronizedList is not a legacy system. It is a newly introduced static method, but comparatively from Vector it is better.

It also has the limitation that it will lock the entire list.

## Problem With Locking the Entire List

What is the problem if you lock the entire list?

If my thread is a read-heavy scenario and my threads are only bothered about reading, then why would you want to lock your collection?

Read is not doing any manipulation to your underlying data structure.

Only when you are writing, doing some modification, update, add, remove, then you are modifying the Collection.

That is the reason why locking your entire list for every type of operation, whether it's a read or write operation, can take a big performance hit.

That is where CopyOnWriteArrayList comes into play.

It is thread safe also and it is going to offer a high performance.

## CopyOnWriteArrayList Read Operation

When we use CopyOnWriteArrayList, it does not use a lock whenever there are read operations.

It relies on a Copy-On-Write strategy.

Whenever there's a write, it does a copy.

### What is a Read Operation?

* Iteration is a read operation.
* Accessing every element.
* Reading the element.
* Trying to do a `get`.

It works on the original array snapshot without any locks.

**Important interview point:**

It works on the original array snapshot without any locks.

Snapshot is like a screenshot.

You take a certain snapshot or that particular time, whatever the state you capture, that state of your data structure.

Without any locks.

There's no external synchronization locking mechanism.

It will read on that snapshot version.

This allows multiple threads to read from the list concurrently without synchronization.

High performance because no locks are there.

You're reading from it, so you have taken a certain state of the data structure, you have captured it, and only on that particular data structure snapshot you're going to do your read operation.

This is the story of the read operation that is happening.

No locks are being used.

It works on the original array snapshot.

## What Happens During Write Operation?

In case of write, what are the write operations?

* Add
* Remove
* Update

In case of that, CopyOnWriteArrayList does use a lock internally which ensures that only one thread can perform a write operation at a time.

Only one thread can perform a write operation at a time.

In that way it is providing thread safety.

## Read vs Write

As a result of that, what happens whenever the read is happening and the write is happening?

It is not clashing because the read is not happening on the underlying data structure.

Why?

It is happening on that snapshot, the previous version probably.

Suppose you have five elements.

The sixth element that you're adding is your write operation.

That is happening on a different array.

Your read is happening on these five elements, the array which you have.

That is the snapshot.

The write is happening on a different array.

What is a different array?

We will again see the cloned or the copied array.

That is why there is no clash.

That is the reason why read versus write has no clash and that is the reason why ConcurrentModificationException is not literally happening.

## Internal Working of CopyOnWriteArrayList During Write

CopyOnWriteArrayList uses a ReentrantLock when it is trying to add an element.

These are the steps happening:

1. It will try to acquire the lock to ensure exclusive access.
2. It creates a new array which is one element larger than the original.
3. Suppose you have five elements, it will try to create an array of six elements.
4. It copies the elements from the original array to the new array.
5. The five elements are copied into your new array.
6. The new array is of six elements.
7. At the end of the new array, you will add that new element.
8. The sixth element is added to the copied array, not to the original array.
9. It updates the reference to the new array.
10. It releases the lock.

It acquires the lock first.

At the end it will release the lock.

Within that it is trying to:

* Create a new array.
* Add that new element to the end of that copied array.
* Point the reference back to it.

All of this is happening when you're trying to do the write operation.

That is why technically read and write are happening on completely two different underlying data structures.

* The write operation is happening on that copied array.
* The read operation is happening on the snapshot version.

This is the technical difference.

## Thread Safety and Consistent View

As a result of that, thread safe additions are being ensured while maintaining consistent view.

The readers will see an older version of the snapshot because the snapshot is having five elements only.

The reader doesn't know that the sixth element is added.

The sixth element is added and that is taken care of by the writer thread.

But it will eventually come.

This is something called eventual consistency also, the model that we know of in system design.

Technically two different data structures.

# Scenario

Let's say we have created a CopyOnWriteArrayList with five elements.

Now the size of the backing array is five.

Backing array is the term we will use for the original array.

It is five.

## Thread 1

There is a Thread 1 which wants to iterate our list.

This is the read scenario.

This Thread will create an iterator.

The returned iterator provides a snapshot for the read operation to happen.

Now Thread 1 is iterating the array.

Which array?

The snapshot array.

## Thread 2

In the meantime another thread, Thread 2, comes in.

It wants to add an element.

If this thread was trying to add the element to our original array, we know ConcurrentModificationException could have been thrown.

This is the ideal scenario when you don't use a CopyOnWriteArrayList.

But to avoid this, what we will do:

* Thread 2 will create a copy of the backing array, the original array.
* Then it will add the new element to this copied array.

Thread 1 will complete its iteration in its own phase, but it will not be able to see the newly added element.

That is obvious because you're working on the older version.

## Thread 3

Then if a new thread, Thread 3, comes in and wants to iterate the list:

* It will create the iterator.
* This time when it gets the snapshot, it has six elements.
* Thread 1 saw five elements.
* Thread 2 added the sixth element.
* Thread 3, which comes in now, will be able to see six elements and not the previous five elements that Thread 1 saw.

This is what is happening behind the scenes of CopyOnWriteArrayList.

# FAQ

## Why would you choose CopyOnWriteArrayList over a regular ArrayList or ArrayList with explicit synchronization?

Unlike explicit synchronization, which requires locking for both read and write:

* Vector class locks for both operations.
* Collections.synchronizedList locks for both operations.
* CopyOnWriteArrayList technically will only lock for the write operation by creating a new copy.
* Reads are entirely lock-free.

That is the reason I will choose CopyOnWriteArrayList.

## What is the performance trade-off?

Nothing comes for free.

CopyOnWriteArrayList has a high memory overhead.

Obviously, we are copying a new array, copying that array, pointing to that reference, all of that.

You need some additional memory because you're keeping a copy of that.

Because of this:

* Writes are slower.
* Reads are fast because they don't require locking.
* It gives you eventual consistency.

It sees you're trying to avoid ConcurrentModificationException.

You want to have thread safe code.

You want to have high performance for reads.

The downside of that is you will get eventually consistent data.

This is the trade-off that you have.

## When is CopyOnWriteArrayList most appropriate in a multi-threading application?

When you need:

* Concurrent read access without worrying about concurrent modifications.
* Writes are infrequent.

If it is a write-heavy system, your writes will be slower because it's making a copy every time.

Your reads will be faster.

It will be uniformly faster only, but your writes will be slower.

You will be using this data structure only when you need a lot of read-heavy kind of a thing, like a read-heavy system.

## What are the downsides or limitations?

Not suitable for scenarios where:

* Writes are more.
* Memory usage is a concern.
* There is a delay between a write and a read.
* Strong consistency is needed.

If you want a system where there is strong consistency needed, like a banking system where your read and write has to happen almost instantaneously, there is no sense of waiting for the records to be consistently updated.

If that kind of strong consistency is needed, you should not use CopyOnWriteArrayList because there is a delay between a write and a read.

So that mismatch can happen.

Consistency mismatch, if it is a concern, you shouldn't use it.

And of course, if writes are more, then you shouldn't use it.

## How does CopyOnWriteArrayList handle iterator concurrency?

The iterators are based on the original snapshot and they're not affected by the modifications.

The iterator will take a snapshot and will go and just iterate over that.

It doesn't bother what has changed in the underlying data structure.

## Can I give an example where it is a good choice?

In GUI frameworks where there's a lot of threads which are trying to read the UI components but not many are updating it, maybe for that it can provide a safe read access without locking while it is trying to render.

Rendering is more like iterating and getting and accessing the elements.

In that case CopyOnWriteArrayList can be a good choice.
