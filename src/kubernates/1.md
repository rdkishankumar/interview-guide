## 1. Your Pod is Running, but users receive 503. What would you check?
A **503 Service Unavailable** error in Kubernetes indicates that the entry point (Ingress Controller, Service mesh, or Load Balancer) cannot route traffic to a healthy backend pod or the application itself is saturated and refusing connections.

---

### Step 1: Check Pod Readiness & Service Endpoints (Most Common Root Cause)

A pod can be in the `Running` phase while failing its **readiness probe**, which causes Kubernetes to strip its IP from the Service's active endpoints.

```bash
# 1. Check if Endpoints exist for the service
kubectl get endpoints <service-name> -n <namespace>
kubectl get endpointslices -n <namespace>

# 2. Check the Pod's readiness status and probe events
kubectl describe pod <pod-name> -n <namespace>

```

* **If Endpoints list is empty (`<none>`):**
* **Failing Readiness Probe:** The container is running, but the probe (`httpGet`, `exec`, or `tcpSocket`) returns non-200 or times out.
* **Selector Mismatch:** The `selector` defined in the `Service` YAML does not match the `labels` on the Pod template in the `Deployment`.
* **TargetPort Mismatch:** The Service's `targetPort` does not match the actual port the application is listening on inside the container.



---

### Step 2: Inspect Ingress & Gateway Configuration

If endpoints exist, the failure may sit at the ingress routing layer:

```bash
# 1. Verify Ingress backend configuration
kubectl describe ingress <ingress-name> -n <namespace>

# 2. Check Ingress Controller logs (e.g., ingress-nginx)
kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=100

```

* **Missing Ingress Backend:** Check if the Ingress rule routes to the exact Service name and port.
* **Certificate / TLS / Upstream Protocol Mismatch:** If the application requires HTTPS but Ingress forwards plain HTTP (or vice versa with gRPC/HTTP2).
* **Ingress Timeout:** If the application takes longer to respond than the Ingress proxy read/connect timeout (e.g., `proxy-connect-timeout` or `proxy-read-timeout`).

---

### Step 3: Check Application-Level Saturation & Queueing

If traffic reaches the container, the application process itself may be throwing the 503:

* **Thread Pool / Connection Pool Exhaustion:**
* Application server (Tomcat, Jetty, Netty, Node.js) has exhausted its worker thread pool or incoming connection queue (`backlog`), rejecting new TCP connections.
* Downstream database connection pools (HikariCP) are exhausted, causing endpoints to fail health checks.


* **Inspect Container Logs:**
```bash
kubectl logs <pod-name> -n <namespace> --tail=200

```


* **Memory Pressure & Stop-the-World GC:** Check if the JVM is frozen in extended Full GC pauses, causing health checks and incoming HTTP requests to time out.

---

### Step 4: Check Service Mesh & Sidecars (Istio / Linkerd)

If using a service mesh with sidecar injection:

* **Sidecar Not Ready:** The Envoy proxy sidecar (`istio-proxy`) might still be initializing or failed to pull Envoy clusters from Istiod.
* **Check Envoy Outlier Detection / Circuit Breaking:**
* Istio's `DestinationRule` might have tripped a circuit breaker due to consecutive 5xx errors, temporarily ejecting the pod from the upstream pool.
* Run:
```bash
istioctl proxy-config endpoints <pod-name>.<namespace>

```





---

### Step 5: Validate Node & Network Layer (CNI / kube-proxy)

* **CNI / IP Table Rules:** Check if the node's CNI plugin (Calico, Cilium, Flannel) or `kube-proxy` failed to program iptables/eBPF routes to the pod IP.
* **Direct Pod Test:** Bypass Ingress and Service to test the pod directly from inside the cluster:
```bash
kubectl port-forward pod/<pod-name> 8080:<container-port>
curl -i http://localhost:8080/health

```



---

### Systematic Troubleshooting Flowchart

```text
[ User Receives 503 ]
       │
       ▼
Check Service Endpoints: `kubectl get endpoints <service>`
       │
       ├──► Empty? ────────► Check Readiness Probes (`kubectl describe pod`)
       │                     Check Service Selector & TargetPort matching
       │
       └──► Populated?
              │
              ├──► Direct Port-Forward works?
              │       ├─► Yes ──► Ingress misconfiguration, TLS mismatch, or proxy timeout
              │       └─► No  ──► App thread/DB pool exhausted, GC freeze, or app-level 503
              │
              └──► Mesh enabled? (Istio/Envoy) ──► Check Circuit Breaker & outlier detection

```
## 2. Your application works inside the Pod but not from outside the cluster. Why?
Here are three senior-level interview answer approaches, ranging from a step-by-step diagnostic breakdown to a direct, high-impact summary:

---

### Option 1: Systematic Layer-by-Layer Diagnostic (The Senior Engineer Standard)

> "If the application responds locally inside the container (`curl localhost:port` or `kubectl port-forward` works) but fails from outside the cluster, the issue lies in the traffic ingress routing pipeline. I would diagnose this top-down across four distinct layers:
> 1. **Service Definition & Endpoint Mapping:**
> * **Service Type:** Verify the Service is exposed via `LoadBalancer`, `NodePort`, or an `Ingress`, rather than the internal-only default `ClusterIP`.
> * **Port Matching:** Check that the Service's `port` and `targetPort` accurately map to the application's listening port.
> * **Endpoints & Selectors:** Run `kubectl get endpoints <svc>` to confirm the Service selector matches the Pod's labels and that the Pod's **readiness probe** is passing. If endpoints are empty, traffic is dropped at the Service level.
>
>
> 2. **Ingress Controller & Gateway Routing:**
> * **Routing Rules:** Check `kubectl describe ingress` to ensure host headers, path prefix matches (e.g., `/api` vs `/api/`), and TLS configurations point to the correct Service name and port.
> * **Ingress Logs:** Check the Ingress Controller logs (e.g., NGINX, ALB, Traefik) for upstream 404, 502, or connection timeout errors.
>
>
> 3. **Application Interface Binding (Common Pitfall):**
> * Check if the application server inside the container is bound strictly to `127.0.0.1` / `localhost` instead of `0.0.0.0` (all interfaces). If bound only to localhost, it accepts intra-container requests but rejects external traffic routed through the virtual network interface (`eth0`).
>
>
> 4. **Infrastructure & Network Security:**
> * **NetworkPolicies:** Check if a Kubernetes `NetworkPolicy` is blocking ingress traffic from the Ingress Controller namespace.
> * **Cloud Infrastructure Firewalls:** Verify that the Cloud Provider's Security Group, AWS ALB/NLB target groups, or external firewall rules permit incoming traffic on the external ports."
>
>
>
>

---

### Option 2: Structured Production-First Angle (The "Hands-On SRE" Pitch)

> "I’d approach this by following the packet path from edge to container:
> * **First, verify Application Binding:** Confirm the app listens on `0.0.0.0` rather than `127.0.0.1`.
> * **Second, check the Service Layer:** Run `kubectl get endpointslices` and `kubectl describe svc` to rule out selector label mismatches, failing readiness probes, or misconfigured `targetPort` mappings.
> * **Third, inspect the Ingress/Gateway:** Verify Ingress path rewrite rules, SSL termination, and check Ingress Controller logs for upstream connection errors.
> * **Fourth, check Network Policies & Cloud Firewalls:** Ensure Kubernetes `NetworkPolicy` allows traffic from the ingress namespace and that Cloud Load Balancers/Security Groups have open inbound ports."
>
>

---

### Option 3: Concise 30-Second Summary (Direct & Punchy)

> "This typically comes down to one of four issues along the ingress chain:
> * **Localhost Binding:** The app inside the container is listening on `127.0.0.1` instead of `0.0.0.0`.
> * **Service Misconfiguration:** Selector labels don't match the Pod, the `targetPort` is wrong, or the Service type is restricted to `ClusterIP`.
> * **Ingress/DNS Mismatch:** Ingress host/path routing rules are misaligned, or SSL termination fails.
> * **Firewall/Network Policy:** A Kubernetes `NetworkPolicy` or Cloud Security Group is blocking incoming external traffic."
